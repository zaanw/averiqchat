# Выпуск первой публичной беты

Кандидат: **0.1.0-beta.1**. Работающий сайт не означает, что все условия публичного релиза выполнены. GitHub Release остаётся черновиком до выполнения обязательных пунктов.

## Обязательные условия

- [ ] Подтверждён собственный домен отправителя в Resend; настроены предложенные сервисом DNS-записи.
- [ ] В Supabase установлен SMTP Resend; подтверждение email остаётся включено.
- [ ] Письмо регистрации и письмо сброса пароля реально получены в контролируемых почтовых ящиках; ссылки открывают правильный сайт.
- [ ] Два аккаунта обмениваются сообщениями, история сохраняется; третьему аккаунту отказано в чтении сообщений и приватных файлов.
- [ ] Проверены Realtime, несколько вкладок, обрыв/возврат сети, повтор отправки без дублей.
- [ ] Проверены группы, выход из группы, права владельца, вложения, правки/удаление, блокировки и жалобы.
- [ ] Последний CI для **точного коммита релиза** успешно завершён. Пропущенные интеграционные тесты не считаются пройденными.
- [ ] Есть резервная копия и успешно выполнено пробное восстановление в изолированном проекте; файлы Storage учтены отдельно.
- [ ] Назначен ответственный за жалобы и доступен контакт поддержки; описание обработки данных заполнено настоящими сведениями владельца.

## Resend

1. Владелец регистрируется на https://resend.com и добавляет свой домен в **Domains**. Адрес `onboarding@resend.dev` не подходит для массовой регистрации.
2. В DNS своего домена публикует записи из Resend и дожидается подтверждения. Приложению не требуется переносить сайт с GitHub Pages на этот домен.
3. Создаёт ключ отправки, ограниченный нужным доменом. Сохраняет его как **RESEND_API_KEY** в секретах среды; разрешённые HTTPS-назначения — `api.supabase.com` (установка SMTP-пароля) и `api.resend.com` (проверка провайдера при наличии разрешения). Значения не помещать в чат, Git, командную строку или workflow inputs.
4. Задаёт обычную переменную **SMTP_FROM**, например `noreply@СВОЙ_ПОДТВЕРЖДЁННЫЙ_ДОМЕН`. Не использовать пример как настоящий адрес.
5. В среде с настроенным доступом выполняет `node scripts/configure-smtp.mjs --apply`. Нужен уже подключённый `SUPABASE_ACCESS_TOKEN`. Скрипт использует SMTP `smtp.resend.com:465`, username `resend`, ключ как SMTP password и сохраняет обязательное подтверждение email.
6. Повторная безопасная проверка конфигурации: `node scripts/configure-smtp.mjs`. Скрипт выводит только статус, не пароли.
7. Проверяет реальные письма регистрации и восстановления. Статус `smtpConfigured: true` сам по себе не подтверждает доставку писем.

Для среды с HTTPS-прокси используйте поддерживаемый Node.js режим `NODE_USE_ENV_PROXY=1` и выданное средой доверенное CA при необходимости. Не отключайте TLS-проверку. Настройка сетевого секрета может подставлять значение только на разрешённом HTTPS-назначении; не пытайтесь извлекать его из прокси.

## Приёмка и публикация

Команды локальных проверок и сценарий двух пользователей находятся в README.

Административный runner: `LIVE_TEST_PROJECT_REF=ТОЧНЫЙ_REF NODE_USE_ENV_PROXY=1 npm run test:live`. Он получает сервисный ключ через уже авторизованный Management API, передаёт его только процессу тестов и создаёт `release-evidence/acceptance.json` с SHA, ref и фактическими счётчиками. Значения ключей не пишутся в файлы. По умолчанию предпочтителен отдельный тестовый проект. Для уже подключённого проекта требуется явное совпадение `LIVE_TEST_PROJECT_REF`; тесты не трогают существующих пользователей.

Пять проверок не отправляют почту: временные пользователи создаются admin API. Шестая, публичная регистрация, запускается только с `TEST_SIGNUP_EMAIL`, принадлежащим оператору и ещё не занятым аккаунтом в проекте. Без этого адреса она skipped, и готовность релиза остаётся false. Подтверждение тестового пользователя admin API не доказывает получение письма.

Результат ручной приёмки хранится локально в `release-evidence/manual.json`: объект с `commit` (полный проверенный SHA), `projectRef` и `checks`. Имена проверок: `emailDelivery`, `passwordRecovery`, `multiTab`, `networkRecovery`, `restoreRehearsal`, `supportContact`. Только фактически выполненные проверки получают `true`; отсутствующие поля означают, что готовность не подтверждена. Не коммитить адреса, пароли и сообщения пользователей. После изменения кода доказательства должны относиться к новому SHA.

Живые интеграционные тесты запускаются отдельно от обычного CI; сервисные ключи никогда не передаются браузеру. Тесты должны создавать только временные собственные аккаунты и очищать только свои записи.

После выполнения всех пунктов обновить этот документ фактическими результатами, CHANGELOG и заметки релиза. Для подготовленного черновика выполнить `npm run release:publish`: команда сначала запускает readiness-check и при любом блокере завершится до изменения Release. Только после успешной проверки она публикует prerelease с тегом `v0.1.0-beta.1` на проверенном коммите. Уже существующий тег на другой SHA не перемещается. Не использовать `--latest` и не называть бету стабильной версией. При провале критического условия оставить релиз черновиком и описать оставшийся блокер.

Откат сайта: вернуть предыдущий проверенный коммит отдельным revert-коммитом и дождаться успешного Pages deploy. Откат frontend не откатывает БД. Перед SQL-изменениями — резервная копия; не удалять данные или миграции ради отката интерфейса.
