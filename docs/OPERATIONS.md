# Эксплуатация Averiq Chat

## Наблюдение

- GitHub Actions → **Production availability**: ежечасная read-only проверка сайта, JavaScript-файлов, доступности Supabase Auth, обязательного подтверждения email и запрета анонимного чтения профилей. Workflow доступен также вручную. Расписание GitHub может задерживаться; это не SLA и не проверка доставки сообщений.
- Владелец включает уведомления GitHub об ошибках Actions в своём аккаунте. Workflow не отправляет письма от имени приложения и не создаёт Issues автоматически.
- Supabase Dashboard → Logs / Reports: Auth, PostgreSQL, Realtime, Storage и использование квот. Не копировать access/refresh tokens, пароли, тела сообщений или приватные файлы в публичные Issues.
- При проблеме регистрации: проверить SMTP/DNS, события доставки Resend, Auth logs и лимит email. Не отключать подтверждение email ради обхода ошибки.
- Клиентского внешнего сборщика ошибок пока нет. Отказы загрузки, подключения и операций показываются интерфейсом. Нельзя заявлять, что ошибки всех браузеров централизованно собираются.

## Резервные копии

На момент подготовки кандидата Management API не вернул ни одной готовой резервной копии; PITR выключен. Наличие `walg_enabled` не доказывает доступность копии для восстановления. Автоматическое резервирование и восстановление пока не проверены.

Перед публичным запуском владелец выбирает поддерживаемые Supabase backup/PITR в рамках своего тарифа либо независимое зашифрованное резервирование через штатные средства PostgreSQL. Не включать платный тариф без решения владельца. Хранить копии отдельно от production и Git, ограничить доступ и задать срок хранения.

Копия PostgreSQL **не содержит байты файлов Storage**. Отдельно резервировать содержимое приватных бакетов через поддерживаемый Storage API/экспорт. Учитывать Auth-пользователей и связи UUID, роли, RLS, функции, публикации Realtime и безопасное восстановление настроек Auth/SMTP. Не размещать ключи и пароли внутри публичных архивов.

Проверка восстановления выполняется в отдельном проекте: восстановить БД и файлы, проверить вход тестовых пользователей, доступ участников, отказ третьему аккаунту, Realtime и подписанные файлы. Записать дату, идентификатор копии, время восстановления и результат без персональных данных. Только после этого отмечать backup-пункт готовым.

## Жалобы

Жалобы находятся в `public.reports`, доступны автору жалобы и доверенному администратору. В Supabase Table Editor администратор просматривает причину и связанное сообщение, принимает решение и фиксирует обработку в своём закрытом журнале. Отдельная панель модерации, автоматическое удаление и уведомление о решении пока не реализованы. Сообщения пользователей не экспортировать в публичные трекеры.

## Чистка файлов и аккаунтов

Незавершённые загрузки, неиспользуемые старые аватары и файлы после сетевой ошибки удаления могут занимать место. Настроить доверенную периодическую очистку: сначала сверить объект с актуальными ссылками БД, выдержать запас времени для активных загрузок и TTL, затем удалить через Storage API. Сначала выполнять dry-run и проверять список. Никогда не удалять `storage.objects` напрямую через SQL.

Пользовательского удаления аккаунта в приложении пока нет. Администратор обрабатывает запросы через контролируемый процесс с учётом сообщений, групп, вложений и резервных копий. Перед открытой регистрацией владелец должен указать доступный контакт поддержки и описать этот порядок пользователям.

## Доступы

Publishable key предназначен браузеру. Service-role / secret API keys и `SUPABASE_ACCESS_TOKEN` — только доверенным административным процессам. Временный токен настройки можно отозвать после завершения работ; работа приложения от него не зависит. Передавать владение группами и администрирование БД через публичные RPC нельзя.
