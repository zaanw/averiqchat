# Averiq Chat

Самостоятельный веб-мессенджер на **Next.js 16, React, TypeScript, Tailwind CSS 4, Lucide, Zod и Supabase**. Оригинальный Midnight-интерфейс, русский язык, светлая и тёмная темы, адаптация под телефон и клавиатуру. Лицензия MIT.

**Текущий статус:** приложение собирается и содержит настоящие интеграции Auth / PostgreSQL / Realtime / Storage. Для онлайн-работы нужно подключить свой Supabase и применить миграцию. Без конфигурации отображается инструкция подключения; фиктивных чатов, аккаунтов и сообщений нет. Проект Supabase подключён к сборке Pages; миграция, приватные бакеты, RLS, Auth redirect URL и приватный Realtime настроены. Полный обмен сообщениями и доставка писем ещё требуют проверки.

## Настройки чатов

Меню → Настройки → Чаты: светлая/тёмная тема, три цвета акцента, размер текста
13–20 px, рисунок или однотонный фон, компактный список разговоров, отправка по
Enter или Ctrl/⌘ + Enter и отключение индикатора набора. Профиль и выход со всех
устройств находятся в отдельных разделах настроек. Настройки чатов сохраняются
в браузере отдельно для каждого аккаунта и синхронизируются между его вкладками;
на другое устройство они не переносятся. При запрете браузерного хранилища
изменения действуют только до закрытия страницы.

Это самостоятельный мессенджер с аккаунтами Supabase. Для входа не нужны
номер телефона Telegram, `api_id` или `api_hash`. Код Telegram Web в приложение
не включён; история и контакты Telegram не импортируются.

## Быстрый запуск

Требования: Node.js 24 LTS, npm, отдельный проект Supabase.

```bash
npm ci
cp .env.example .env.local
# Заполните две NEXT_PUBLIC_ переменные (см. ниже).
npm run dev
```

Откройте адрес, указанный Next.js. Для нескольких людей через интернет разверните приложение на GitHub Pages или Vercel по HTTPS. Локальный сервер сам по себе не делает приложение доступным другим людям.

## Подключение Supabase — по шагам

1. Создайте проект в Supabase. Сохраните пароль БД в менеджере секретов.
2. В **SQL Editor** выполните миграции **по порядку**, каждую один раз: `supabase/migrations/202610270001_initial.sql`, затем `supabase/migrations/202610270002_chat_tools.sql`, затем `supabase/migrations/202610280001_saved_reactions.sql`. На существующем проекте выполняйте только ещё не применённые миграции. Миграции транзакционные; первая создаёт таблицы, ограничения, RPC, RLS, приватные Storage-бакеты и подписки PostgreSQL Changes; вторая — личные папки, закрепления и поиск сообщений; третья — личные заметки и реакции. Не запускайте их повторно и не применяйте к чужой существующей схеме без ревью.
   Альтернатива для проекта с настроенным Supabase CLI: `supabase link --project-ref YOUR_REF`, затем `supabase db push`. Аутентификацию CLI и пароль БД задавайте через штатный защищённый механизм CLI.
3. В **Project Settings → API / Connect** возьмите Project URL и **publishable key** (`sb_publishable_…`) или legacy **anon key**. В `.env.local`:

   ```dotenv
   NEXT_PUBLIC_SUPABASE_URL=https://YOUR_REF.supabase.co
   NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_PUBLISHABLE_OR_ANON_KEY
   ```

   Эти две настройки публичны по назначению. **Никогда не используйте здесь secret / service_role key**, пароль БД или SMTP-пароль. Сервисный ключ не нужен работающему приложению.

4. В **Authentication → Providers → Email** включите Email и **Confirm email**. Минимальную длину пароля задайте 12. Настройте SMTP для реальной доставки: встроенный почтовый сервис ограничен и не рассчитан на публичный продукт. Настройте Auth rate limits для signup, login и recovery под вашу нагрузку.
5. В **Authentication → URL Configuration** укажите Site URL вашего сайта и разрешённые redirect URL:
   - `http://localhost:3000/auth/confirm/`
   - `http://localhost:3000/reset-password/`
   - `https://YOUR_DOMAIN/auth/confirm/`
   - `https://YOUR_DOMAIN/reset-password/`

   Для локального IP-адреса или другой среды добавьте её **точные** callback URL отдельно. Не используйте глобальное `*` для production.

6. В **Realtime Settings** разрешите приватные каналы с авторизацией. Приложение подписывается на `chat:<conversation UUID>` с `private: true`; политики `realtime.messages` проверяют членство. Не заменяйте их публичным доступом. Миграция добавляет `messages`, `conversations`, `conversation_members` в публикацию `supabase_realtime`.
7. В **Storage** проверьте три **приватных** бакета: `attachments`, `avatars`, `group-avatars`. Не включайте public access. Лимиты и MIME-типы задаёт миграция. Для вложений: до 10 МБ, JPG/PNG/WebP/PDF/TXT; для аватаров: до 2 МБ, JPG/PNG/WebP.
8. Перезапустите dev-сервер после изменения `.env.local`. Для production выполните новую сборку: `NEXT_PUBLIC_*` встраиваются Next.js во время build.

Подтверждение email и восстановление пароля используют Supabase PKCE. Ссылку из письма открывайте в том же браузере, где начали операцию (браузер хранит PKCE verifier). Код ссылки обрабатывает официальный Supabase SDK; пароль и auth-коды приложение не логирует.

## Возможности

- «Избранное»: меню → Избранное. Личный чат для заметок и файлов, без приглашения других участников. Создаётся при первом открытии, сохраняется в базе и доступен на ваших устройствах.
- Реакции на сообщения: шесть эмодзи, по одному выбору на участника. Повторный клик убирает реакцию; новый эмодзи заменяет старый. Счётчики обновляются после изменения и с фоновым обновлением истории (до 5 секунд). Доступ проверяется на сервере; удаление сообщения убирает его реакции.

- Закрепление и открепление чата: меню «⋯» в шапке → «Закрепить чат». Закреплённые разговоры выше остальных.
- Личные папки: меню «⋯» → «В папку». У чата одна папка; название до 24 символов. Папки видны только владельцу, пустые исчезают. Переключатель папок появляется под вкладками чатов.
- Папки и закрепления сохраняются в Supabase, обновляются после изменения и при фоновом обновлении списка (до 15 секунд на другом устройстве/вкладке).
- Поиск по всей текстовой истории выбранного чата: лупа в шапке, 2–100 символов, по 50 результатов с загрузкой более ранних. Регистр не учитывается, спецсимволы ищутся буквально. Можно ответить из результата; удалённые сообщения исключены. Это поиск по тексту, без OCR и содержимого файлов.

- Регистрация, подтверждение email, вход, восстановление пароля, выход на устройстве или завершение всех сессий.
- Уникальный нормализованный `@username` (3–24 символа, латинские буквы/цифры/_, первая буква), имя и приватные аватары.
- Поиск только **по точному юзернейму**, без открытого каталога и без email в профилях.
- Личные чаты с атомарным созданием единственной беседы для пары пользователей.
- История с постраничной загрузкой, Realtime, ответы, редактирование и удаление своих сообщений, эмодзи.
- UUID отправки предотвращает дублирование при повторе запроса. При неопределённом результате отправки текст блокируется до повторной попытки; ошибку соединения приложение показывает пользователю.
- Одна галочка означает **сохранено в БД**, две — все остальные текущие участники отметили чат прочитанным. Отдельного неподтверждённого статуса «доставлено на устройство» нет. Чат отмечается прочитанным только в видимой активной вкладке у конца истории.
- Индикатор набора через Presence с таймаутом, автоматический reconnect SDK, повторная загрузка при подписке / возврате фокуса / восстановлении сети; резервное обновление активного чата каждые 5 секунд, списка чатов каждые 15 секунд. Вкладки синхронизируют auth через SDK и историю через БД.
- Группы до 50 участников: название, аватар, владелец/участник, приглашение по юзернейму, выход. Владелец приглашает, меняет название и аватар; выйти он может только из группы без других участников. Передача владения не реализована.
- Изображения и документы: загрузка, метаданные, приватные подписанные ссылки, предпросмотр изображений по нажатию.
- Блокировка запрещает **новые личные сообщения в обе стороны**, история остаётся доступна участникам. Блокировка не скрывает сообщения в общих группах.
- Жалобы сохраняются приватно. Администратор проекта разбирает их через Supabase Dashboard; отдельной панели модерации и автоматического рассмотрения нет.

## Архитектура и безопасность

```text
app/                      Страницы входа, callback, восстановления
components/               UI и клиентские сценарии
lib/                      Клиент Supabase, Zod, типы и ошибки
supabase/migrations/      Вся серверная модель и политики
  profiles                Профили без email
  conversations           Личные чаты / группы
  conversation_members    Участники, роль, время прочтения
  conversation_preferences Личные папки и закрепления
  saved_conversations      Личные чаты для заметок
  message_reactions        Реакции участников
  messages                Текст, ответ, правки, tombstone удаления
  attachments             Приватные пути и привязка к сообщению
  blocks / reports        Блокировки / жалобы
  private.rate_limits     Серверные счётчики запросов
tests/                    Unit, PostgreSQL, браузер, интеграция
```

Браузер напрямую использует Supabase с публичным ключом и пользовательским JWT. SSR не принимает решений о правах: их обеспечивает БД. RLS включён на всех пользовательских таблицах, серверных счётчиках и Storage / Realtime. Клиент не может напрямую вставлять/менять сообщения или членство: только ограниченные RPC. `SECURITY DEFINER` функции используют пустой `search_path`, проверяют `auth.uid()`, членство/авторство/роль. Вспомогательные функции лежат в закрытой схеме `private`. Права `EXECUTE` для анонимных клиентов отозваны.

Доступ к профилям: свой профиль и профили собеседников. Точный поиск возвращает только профиль найденного человека (email в таблице нет). Связь `reply_to` и вложение должны относиться к той же беседе. Чужое вложение нельзя привязать к своему сообщению. Пути Storage содержат UUID беседы и загрузившего пользователя; политики дополнительно проверяют членство.

Ограничения RPC: отправка/редактирование — 30 успешных операций в минуту отдельно; создание бесед — 10/мин; поиск/приглашения/регистрация вложений/блокировки — 20/мин; жалобы — 5/час. Счётчики атомарны, ошибки откатывают транзакцию; это ограничение успешных операций, а не защита от сетевого DDoS. Реакции, поиск сообщений и изменение личных папок/закреплений ограничены 60 успешными вызовами в минуту на пользователя для каждого действия. Сохраняйте встроенные Auth / Storage / API ограничения Supabase и настройте квоты проекта перед публичным запуском.

Аутентификацией, refresh токенами и синхронизацией сессий между вкладками управляет официальный SDK. Сессия хранится SDK в браузере. Используйте HTTPS, не подключайте непроверенные скрипты. При global sign-out refresh токены отзываются, но ранее выданные access JWT действуют до истечения; задайте подходящий срок JWT в Supabase (например, 15 минут).

**Ограничения приватных файлов:** подписанная ссылка является временным bearer-доступом (60 секунд для вложений, 5 минут для аватаров). Уже выданная ссылка не отзывается мгновенно после выхода из группы или удаления сообщения; она истекает по TTL. Новую ссылку без прав получить нельзя. После удаления сообщения метаданные удаляются атомарно, клиент отдельно удаляет физический объект через Storage API. При обрыве связи могут остаться недоступные объекты или незавершённые загрузки; настройте периодическую очистку через доверенный backend с Storage API. **Не удаляйте `storage.objects` через SQL**. Предыдущие аватары также требуют периодической очистки. Антивирусная проверка и анализ сигнатур файлов не реализованы: ограничения MIME/размера не заменяют их.

Сквозного шифрования нет. Доступ администраторов инфраструктуры к данным не исключён. Нет звонков, push-уведомлений, офлайн-очереди, передачи владения и независимого аудита безопасности. Для production нужны SMTP, резервные копии, мониторинг квот, обработка жалоб и проверка сценариев ниже.

## Проверки

```bash
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install --with-deps chromium
npm run test:e2e
```

Если Chromium уже установлен (как в подготовленной облачной среде):

```bash
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

- Vitest: валидация входных данных и исполнение **реальной SQL-миграции** в PGlite (PostgreSQL WASM), проверки RLS, разных пользователей, уникальности username, прав автора, ролей, блокировки, жалоб, повторной отправки, приватности Storage/Realtime и частоты сообщений. Минимальные служебные схемы `auth`, `storage`, `realtime` в этом тесте воспроизводят интерфейсы для SQL — это **не проверка сервисов Supabase**.
- Playwright: Chromium desktop и мобильный viewport, честное состояние без конфигурации, регистрационная форма, сброс пароля, клавиатура, отсутствие горизонтальной прокрутки. Эти тесты запускайте *_без NEXT_PUBLIC_SUPABASE__ в окружении и без заполненного `.env.local`**. Тесты не отправляют письма и не подставляют вымышленные сообщения в продукт.
- Настоящие Auth / Realtime / Storage тесты находятся в `tests/supabase.integration.test.ts`, по умолчанию **пропущены**, пока не заданы все `TEST_SUPABASE_*`. Локальный `.env.local` Vitest автоматически не читает: передавайте переменные через защищённую среду запуска/CI, не коммитьте значения.

Для интеграционных тестов предпочтительно использовать **отдельный тестовый Supabase-проект** с этой миграцией, включённым подтверждением email и разрешённой отправкой тестовых писем / тестовым SMTP. Задайте `TEST_SUPABASE_URL`, `TEST_SUPABASE_ANON_KEY`, `TEST_SUPABASE_SERVICE_ROLE_KEY` только процессу тестов; сервисный ключ никогда не должен попадать в `NEXT_PUBLIC_*`. Тесты создают временные аккаунты, проверяют регистрацию, отказ входа до подтверждения, подтверждают пользователя через admin API, входят под разными аккаунтами, проверяют реальную доставку Realtime, RLS, Storage и группы, затем очищают данные. Реальную доставку письма в почтовый ящик они не проверяют. Публичная регистрация требует `TEST_SIGNUP_EMAIL` с контролируемым, ещё не занятым адресом; иначе эта проверка skipped. В подключённом проекте тесты разрешены только с явным `TEST_SUPABASE_ALLOW_PROJECT`, равным ref проекта. Административный runner и точные условия релиза описаны в docs/RELEASE.md. При прерванном запуске удалите `averiq-…@example.com` тестовые аккаунты и оставшиеся объекты из тестового проекта.

### Приёмка после подключения (два браузера)

1. Зарегистрируйте A и B с разными email и username. Проверьте вход до подтверждения (должен отказать), откройте ссылки из писем и войдите.
2. A находит точный @username B. Отправьте сообщения в обе стороны; перезагрузите страницы — история остаётся. Откройте ещё одну вкладку A, проверьте синхронизацию, ответы, редактирование, удаление и набор текста.
3. Третий аккаунт C не должен получить сообщения/файлы беседы A/B ни из API, ни по подписке. Это также проверяет интеграционный тест.
4. Попытайтесь занять username A у B — получите ошибку. Восстановите пароль по письму; старый пароль больше не работает.
5. Создайте группу, пригласите участника, проверьте отказ приглашения от обычного участника и потерю доступа после выхода. Измените аватар/название владельцем.
6. Загрузите JPG и PDF. Проверьте предпросмотр, получение другим участником, отказ для C и отказ для SVG / файлов больше лимита.
7. Проверьте блокировку, жалобу, два статуса сохранения/прочтения. Отключите сеть, затем включите: ошибка видна, история восстанавливается, повтор отправки не дублирует сообщение.
8. Повторите на телефоне. Проверьте Tab/Shift+Tab, Escape и удержание фокуса в модальных окнах, Enter/Shift+Enter в редакторе.

## Деплой на GitHub Pages

GitHub Pages размещает статический интерфейс; Supabase остаётся настоящим backend. Node.js-сервер на Pages не нужен. Workflow `.github/workflows/pages.yml` собирает `out/` и публикует его при push в `main` или ручном запуске **Actions → Deploy GitHub Pages → Run workflow**.

1. Загрузите этот код в `zaanw/averiqchat`, ветку `main`.
2. В репозитории откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**. Для приватного репозитория доступность Pages зависит от тарифа GitHub.
   Если workflow сообщает `Get Pages site failed: Not Found`, сначала проверьте этот выбор. У build-job должно быть `pages: read` (уже задано в workflow). Параметр `enablement: true` без отдельного токена администратора не создаёт сайт: стандартного `GITHUB_TOKEN` для первоначального включения недостаточно. Для ручного включения сайта дополнительный токен не нужен.
3. Для текущего сайта публичные URL и publishable key уже записаны в `config/supabase.public.json`: Pages использует их при сборке. Это публичные, предназначенные браузеру значения; административных ключей в этом файле быть не должно. Для другого проекта или переопределения в **Settings → Secrets and variables → Actions → Variables** добавьте две repository variables: `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Это публичные настройки Supabase, не service role ключ. Без repository variables текущая сборка использует публичную конфигурацию из `config/supabase.public.json`.
4. Примените SQL-миграцию и настройте Supabase по инструкции выше. Для стандартного project Pages задайте Site URL `https://zaanw.github.io/averiqchat/`, а redirect URL **точно с завершающим слешем**:
   - `https://zaanw.github.io/averiqchat/auth/confirm/`
   - `https://zaanw.github.io/averiqchat/reset-password/`
5. Запустите workflow. Адрес действующего сайта появится в успешном шаге deploy и в **Settings → Pages**. Обычно для этого репозитория это `https://zaanw.github.io/averiqchat/`; пока deploy не прошёл, этот адрес не считается опубликованным.
6. После добавления/изменения переменных повторно запустите workflow — публичные настройки встраиваются в сборку. Пройдите приёмку двумя аккаунтами.

`actions/configure-pages` передаёт реальный `base_path` в сборку, поэтому project Pages, user Pages и собственный домен используют правильный префикс. Browser callback URL учитывают этот префикс. При смене домена обновите Supabase Site URL / redirect URL и повторите deploy.

Локальная проверка именно артефакта Pages:

```bash
SUPABASE_UNCONFIGURED_TEST=1 npm run build:pages
# Изолированная сборка без backend для браузерных тестов.
# Обычная npm run build:pages использует подключённый проект.
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:pages
```

Если системного Chromium нет, сначала установите его через `npx playwright install chromium`, затем выполните `npm run test:pages`. Два теста (desktop/mobile) проверяют статику, JS/CSS и прямой вход на вложенные auth-страницы, включая возврат в `/averiqchat/`. Для теста конфигурация Supabase должна отсутствовать. Для собственного пути задайте `NEXT_PUBLIC_BASE_PATH` при сборке; браузерный тест проверяет стандартный путь `/averiqchat/`.

Pages workflow выполняет read-only live-проверку Auth, обязательного подтверждения email и запрета анонимного чтения профилей. Это не проверка доставки письма или переписки двух аккаунтов. SMTP в подключённом проекте пока не настроен: встроенный почтовый сервис Supabase ограничивает получателей и частоту, для публичной регистрации нужен собственный SMTP. Подтверждение email остаётся включённым.

На GitHub Pages не применяются HTTP-заголовки из `next.config.ts` — их поддерживает только режим с Next.js-сервером. Режим Pages отключает эту серверную настройку, использует `output: export` и `trailingSlash: true`. Не полагайтесь на серверные headers приложения на Pages; контроль доступа по-прежнему обеспечивает Supabase RLS.

### Проверка интерфейса чата

`npm run build:pages`, затем `npm run test:chat` (или с `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium`). Эти desktop/mobile тесты используют **только тестовые ответы Supabase**, перехватывают сетевые запросы и не создают аккаунтов/сообщений в реальном проекте. Проверяются фильтры чатов, мобильный возврат к списку, группировка сообщений, рост редактора, отображение отправленного сообщения при недоступном Presence и переключение темы. Это UI-тесты; они не заменяют интеграцию с настоящим backend. В продукте этих данных нет.

## Деплой на Vercel

1. Сохраните код в своём GitHub-репозитории. Workflow `.github/workflows/ci.yml` запускает lint, typecheck, unit/SQL тесты, build и браузерные проверки; удалённые Supabase-тесты без ключей остаются skipped.
2. В Vercel импортируйте репозиторий, framework **Next.js**, Node.js **24.x**, команда сборки `npm run build`.
3. Добавьте `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY` в нужные окружения Vercel. Не добавляйте service role ключ.
4. Выполните deploy. Установите финальный HTTPS домен как Supabase Site URL; добавьте точные `/auth/confirm/` и `/reset-password/` redirect URL. Для preview-доменов используйте отдельный Supabase-проект и ограниченный список URL.
5. Если меняли публичные переменные — redeploy. Пройдите приёмку двумя реальными аккаунтами перед приглашением пользователей.

Автоматический деплой и публикация в GitHub этим проектом не выполняются. Секреты в GitHub Actions не нужны для обычного CI. Дополнительный прогон интеграции включайте только для доверенных веток и отдельного тестового backend, не отдавайте service role секрет в PR из fork.
